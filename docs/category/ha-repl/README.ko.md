# `ha_repl` 카테고리

*[English](README.md) · 한국어*

`ha_repl` 은 독립된 task 다. `sql` 코퍼스를 가져와 마스터에서 돌리고, 슬레이브가 같은 것을
갖게 되는지 확인한다 — 그러니까 `sql` 스위트의 질문을 답 파일이 아니라 **페어에 걸쳐** 묻는
것이다.

HA 라는 말을 쓰는 다른 하나는 [`ha-shell`](../ha-shell/README.ko.md) 이다. 둘은 오라클을
공유하고 그 외에는 거의 아무것도 공유하지 않는다:

| | **[`ha-shell`](../ha-shell/README.ko.md)** | **`ha_repl`** |
|---|---|---|
| 무엇을 묻는가 | 복제가 *이것* 을 견디는가 — 멈춘 노드, 재시작된 서비스, 다시 만든 슬레이브 | 복제가 *이 SQL* 을 올바르게 옮기는가 |
| 누가 토폴로지를 움직이는가 | 케이스가. 373 중 263 이 그렇게 한다 | **아무도.** 구조상 정상 상태 |
| 누가 페어를 만드는가 | 케이스가 `make_ha.sh` 를 불러서 | **러너가** |
| 코퍼스 모양 | 셸 스크립트 | 변환된 `sql` 코퍼스 |
| 동결 | 그렇다 | **아니다** — 변환은 동결 대상이 아니다 |

| | |
|---|---|
| **[2. 케이스 쓰기](02-writing-a-case.ko.md)** | 변환이 무엇을 바꾸는지, 그리고 그대로 넘어오는 한 가지 규칙 |

**이제 네이티브 러너가 있고**, `TESTKIT_NATIVE=ha_repl` 뒤에 있다. 이 문서의 나머지가 그
as-built 가이드다. 그 스위치가 없으면 task 는 여전히 CTP 에 서브프로세스로 그대로 넘어간다 —
[무엇이 어디서 도는가](../../../README.ko.md#무엇이-어디서-도는가) 참조.

게이트가 특이한 부분이고, 더 읽기 전에 알아둘 값이 있다: 이 러너는 CTP 와의 parity 비교를
**기다리지 않는다**. 그 이유는 [ADR-015](../../project/adr/ADR-015-beyond-axis.md) 에 개정으로
적혀 있다. CTP 는 같은 코퍼스에 `CALL` 로 시작하는 모든 구문과 `INCR` 또는 `DECR` 을 담지 않은
모든 `SELECT` 를 지우는 변환을 거쳐 닿는다. 그것에 대한 parity 는 **다른 코퍼스**에 대한
주장이다 — 그리고 이 러너의 오라클인 케이스 자신의 read 가 바로 그 지워지는 구문들 안에 있다.

---

## 이 스위트는 무엇을 위한 것인가

**정지해 있는 토폴로지 위에서, 한 구문에 대해 복제가 올바르다는 것을 establish 한다.** 토폴로지가
교란을 견디는지가 아니다 — 그것은 [`ha-shell`](../ha-shell/README.ko.md) 의 일이고, `ha_repl` 은
그 일을 아예 하지 않는다: 스무 남짓한 Java 파일 중 `hb stop` 을 언급하는 것은 둘 셋뿐이며 그것도
배포와 정리용이다.

그래서 둘 중 더 좁고 더 날카로운 쪽이다. 여기서의 실패는 **특정 SQL 구성에 대한 복제 결함**이고,
그것을 설명할 수 있는 다른 움직이는 것이 없다.

## 오라클, 두 번 도달된 것

케이스가 마스터에서 돌고, 그 다음 **두 노드에 같은 질문을 던져 답을 비교한다.** 기록된 답과
대조하는 것은 아무것도 없다.

두 구현이 그것을 묻는 방식이 다르고, 그 차이가 중요하다:

| | 페어에 묻는 방식 |
|---|---|
| CTP 의 러너 | 두 노드를 덤프해서 덤프를 diff 한다 |
| 이 러너 | **케이스 자신의 read** 를 두 노드에서 다시 돌려 답을 diff 한다 |

어느 쪽이든 [`ha-shell`](../ha-shell/README.ko.md#오라클-그리고-그것이-왜-좋은-부분인가) 과 같은
오라클이고, 두 스위트가 여기에 **독립적으로** 도달했다. 그것이 이 오라클이 HA 에 옳다는 가장
강한 증거다: 낡아갈 기대 출력이 없고, 엔진의 출력 형식이 바뀌어도 다시 기록할 것이 없으며,
비교는 같은 빌드를 돌리는 두 노드 사이에서 일어난다.

그리고 그것이 변환이 존재하는 *이유* 다. `sql` 코퍼스의 케이스들은 각각 실행 결과를 기록한
`.answer` 파일을 들고 있는데, 케이스를 `ha_repl` 로 변환한다는 것은 **답 파일이 오라클이길
그만두고** 슬레이브가 그 자리를 차지한다는 뜻이다.

케이스 자신의 read 를 남기는 데는 분명히 말해둘 결과가 하나 더 있다: **빼놓을 구문의 목록이
존재할 수 없다.** 아무것도 다시 쓰지 않기 때문이다. CTP 의 변환에는 그런 목록이 있고, 거기에
무엇이 올라 있는지가
[그 자체로 하나의 발견](../../project/evidence/ha/ctp-ha-repl-deletes-the-call.md)이다.

## 그 기다림, 같은 기다림

`Test.java` 는 마스터에 플래그를 쓰고 슬레이브에서 `GOOD-<id>` 를 폴링하며, 시도 사이에 backoff
하고 `ha_sync_detect_timeout_in_ms` 에서 포기한다.

shell 쪽 CTP 의 `wait_for_slave` 가 다른 경로로 같은 일을 하고,
`internal/sandbox.WaitForReplication` 은 둘을 개선하는 대신 **둘에 맞추어** 쓴 세 번째 구현이다.
하나의 모양에 세 번 도달했다는 것이
[`module-ha.md`](../../project/design/module-ha.md) §4 P1 이 그것을 선호가 아니라 **성질**로
진술하는 이유다: **동기화는 상태에 대한 폴링이지 결코 sleep 이 아니다.**

## 네이티브 러너를 한 문단으로

코퍼스 하나와 master/slave 페어 하나를 가리키면 된다. 케이스마다 러너는 데이터베이스를 지우고,
케이스의 구문들을 마스터에서 돌리고, 자기가 만든 마커가 슬레이브에 나타날 때까지 기다린 다음,
**케이스 자신의 read 를 두 노드에서 다시 돌려 답을 비교한다.** 답 파일도, 덤프 diff 도 없다 —
오라클은 두 노드가 엇갈리는 것 자체다.

## 가장 짧은 런

페어는 [`cluster-sandbox`](../extensions/README.ko.md) (`csb`) 에서 온다. `extensions/cluster-sandbox`
에 고정돼 있다. **러너는 토폴로지를 절대 만들지 않는다. 요청할 뿐이다**
([ADR-022](../../project/adr/ADR-022-topology-provider.md)).

```bash
csb cluster create --cluster hadb --build /path/to/CUBRID --preset ha

cat > /tmp/ha.conf <<'EOF'
scenario=/path/to/cubrid-testcases/sql/_01_object
sandbox_cluster=hadb
EOF

TESTKIT_NATIVE=ha_repl testkit ha_repl -c /tmp/ha.conf
```

케이스가 판정될 때마다 한 줄씩 찍고, 끝나면 요약과 페어별 집계를 찍는다.

## 판정값, 그리고 왜 아홉 개인가

여기서 케이스는 단순히 통과하거나 실패하지 않는다. 복제는 올바를 수도, 틀릴 수도, **해당하지
않을 수도**, 아예 물어지지 않았을 수도 있다 — 그리고 그것들을 뭉개면 **CUBRID 의 설계를 결함으로
보고하게 된다.**

| 판정값 | 뜻 |
|---|---|
| `same` | 케이스가 썼고, 기다림이 돌아왔고, 모든 사용자 테이블이 두 노드에서 동일하게 읽힌다. 이 스위트가 존재하는 이유인 값 |
| `differ` | **발견.** 복제를 기다린 *뒤에* 내용이 엇갈린다 — "가는 중" 과 "도착하지 않을 것" 의 차이 |
| `replicating` | 케이스가 썼고, 비교 가능한 read 를 만들지 않았고, 그 쓰기는 건너간 것이 확인됐다. `same` 보다 적고 아무것도 아닌 것보다는 많다: 그 케이스의 데이터가 일치한다는 게 아니라, 도는 동안 페어가 복제 중이었다는 것 |
| `no_data` | 케이스가 읽기 전용이다. `sql` 코퍼스의 상당수가 그렇고, 정직한 주장은 두 노드 어디서도 아무 일도 없었다는 것이다 |
| `unreplicatable` | 모든 read 가 **기본키 없는** 테이블에 닿는다. CUBRID 의 데이터 복제는 기본키를 키로 삼으므로 그 행들은 애초에 건너갈 수 없었다. 실패가 아니라 — **이 코퍼스가 물을 수 없는 질문**이다 |
| `session_differs` | 두 노드가 read 를 서로 다른 사용자로 돌려서 답을 비교할 수 없다. 대개 실제 복제 문제의 증상이지만, 그 자체가 복제에 대한 판정은 아니다 |
| `wait_timeout` | 복제가 제한 시간 안에 도착하지 않았다. `differ` 와 따로 보고되는데, 처방이 같지 않기 때문이다 |
| `case_failed` | 마스터가 케이스 자신의 SQL 을 거부했다. 복제 발견이 아니다 — 케이스가 발견을 만들 만큼 나아가지 못했다 |
| `skipped` | 케이스의 세미콜론이 전부 구문 종결자는 아니라서, 쪼개면 조각을 실행하게 된다. 시도하거나 숨기는 대신 **이름을 대고 센다** |

## 설정

| 키 | 기본값 | 무엇을 하는가 |
|---|---|---|
| `scenario` | — | 코퍼스 루트. `cases/` 디렉터리 아래의 모든 `*.sql` 이 케이스다 |
| `sandbox_cluster` | — | 페어. **쉼표로 나열하면 코퍼스를 여러 페어에 걸쳐 동시에 돌린다** — 아래 참조. `TESTKIT_CSB_CLUSTER` 가 덮어쓴다 |
| `ha_sync_detect_timeout_in_ms` | `60000` | 마커가 건너가는 데 주는 한계. 기다림 자체는 상태에 대한 폴링이지 결코 sleep 이 아니다 |
| `add_primary_key` | `no` | 기본키 없는 `CREATE TABLE` 에 생성된 기본키를 준다. 그래야 그 행들이 복제될 수 있다. **기본이 off 인 이유**: 변환되지 않은 런이 변환을 측정할 기준선이고, 기본으로 켜진 스위치는 그것을 가린다 |
| `reset` | `case` | `case` 는 케이스마다 데이터베이스를 지우고, `dir` 은 디렉터리 경계에서 지운다. 후자가 `sql` 코퍼스 자신의 계약이 전제하는 것이다 |
| `resume` | `no` | 이전 런이 이미 판정한 케이스를 건너뛴다 (아래 원장 참조) |
| `status_http` | 꺼짐 | `on` 이면 `:51523` 에 실시간 상태 페이지를 연다. `host:port` 나 `:port` 를 주면 다른 곳에 연다 |
| `difference_dir` | conf 옆 | 차이, 원장, 리포트가 쓰이는 곳 |

## 한 런으로 여러 페어 돌리기

`sandbox_cluster=a,b,c,d` 는 **한 프로세스**로 네 페어를 몬다.

이것은 의도적으로 네 프로세스가 아니다. testkit 의 프론트엔드는 설계상 한 번에 하나의 테스트다 —
결과 트리는 한 런의 락을 가져간다 (`internal/result/lock.go`) — 그래서 여덟 번 호출하면 여덟
런이 하나의 기록을 두고 다투게 된다. 한 프로세스 안에는 기록 하나, 페이지 하나, 원장 하나가
있고, **여럿인 것은 페어뿐이다.**

**코퍼스가 어떻게 나뉘는지는 `reset` 에 달려 있고**, 이것은 보기보다 중요하다:

- `reset=dir` 에서는 디렉터리가 통째로 배분된다. 그 안의 케이스들이 서로 의존할 수 있는 단위이기
  때문이다. 그러면 큰 디렉터리 하나가 런의 바닥을 정한다: `_01_object` 의 가장 큰 디렉터리가
  3,327 중 867 을 갖고 있어서, **네 페어와 열여섯 페어가 같은 시각에 끝난다.**
- `reset=case` — 기본값 — 에서는 케이스 단위로 배분된다. 어차피 케이스마다 데이터베이스를
  지우므로, 디렉터리를 통째로 두는 것이 보호하던 의존은 **러너 자신이 이미 끊어놓았고**, 함께
  둘 이유가 남아 있지 않다.

이 코퍼스에서 측정된 값: 13 디렉터리에 걸친 290 케이스가 한 페어에서 142 초, 여덟 페어에서
31 초. 16 코어 호스트에서 8 중 병렬일 때 케이스당 비용이 약 1.5 배 오르고, 그것이 깨끗한 8 배와의
차이다.

**페어는 닳는다.** 타이밍을 비교하기 전에 알아둘 값이다. 케이스별 리셋은 스키마를 지우지만,
데이터베이스가 늘린 볼륨도 복제 사본 로그도 돌려주지 않는다. 수만 구문을 돌린 페어는 새 페어보다
케이스당 몇 배를 치르고, 샤딩된 런에서는 **닳은 페어가 벽시계를 정한다**
([`evidence/ha/a-sandbox-pair-wears-out.md`](../../project/evidence/ha/a-sandbox-pair-wears-out.md)).

## 런이 남기는 것

전부 `difference_dir` 아래에 떨어진다.

**`verdicts.tsv` — 원장.** 케이스마다 한 줄씩, 판정이 나는 대로 덧붙여 flush 한다: 케이스,
판정값, 상세, 밀리초. 이것이 존재하는 이유는 3,327 케이스 런이 한 시간이 넘고, 한 시간은 무관한
무언가에 방해받기 충분히 길기 때문이다 — 2026-09-22 에 두 번, 호스트의 모든 CUBRID 프로세스가
같은 밀리초에 멈췄다. `resume=yes` 는 그것을 다시 읽어 판정된 것을 건너뛰되, **`wait_timeout` 과
`case_failed` 는 제외**한다. 그 둘은 케이스가 아니라 런에 대한 판정이라, 재개하면 방해가 입힌
손상을 다음 런의 집계로 끌고 와 그것을 측정값이라 부르게 된다.

**차이마다 디렉터리 하나** — 구문, 두 노드의 원본 출력, 정규화된 diff 를 담는다. 그래서 `differ`
하나를 아무것도 다시 돌리지 않고 읽을 수 있다.

**`slave-stranded.tsv`** — 케이스가 리셋으로 지울 수 없는 객체를 슬레이브에 남겼을 때. 스위트는
안전하게 할 수 있는 것은 복구하고 **복구했다는 사실을 기록한다.** 그러지 않으면 독자가 의도적으로
갈라진 코퍼스와 실수로 갈라진 것을 구분할 수 없기 때문이다.

## 상태 페이지, 그리고 이미 돌고 있는 런을 보는 법

`status_http=on` 은 런이 사는 동안 `:51523` 에 페이지를 연다: 페어마다 레인 하나, 각자가 지금
어느 케이스에 있는지, 그리고 페어마다 패널 하나 — 두 노드의 역할, HA 상태, applied·copied 페이지
ID, lag, `fail_counter`, 지금 걸려 있는 fault, 그리고 그 클러스터가 무엇으로 만들어졌는지의
아티팩트. 이것들이 페이지에 있는 이유는 **각각의 부재가 값을 치렀기 때문이다** — 서빙을 멈춘
페어가 한 번은 한 시간짜리 런을 케이스마다 `wait_timeout` 으로 만들었고, 그것은 정직하게
보고되었으나 아무도 알아차리지 못했다.

런이 이미 돌고 있는데 페이지를 켜지 않았거나 닫았다면:

```bash
testkit watch
```

`/proc` 에서 각 프로세스의 명령줄을 읽어 이 머신의 `ha_repl` 런들을 스스로 찾고, 그 전부를 덮는
페이지 하나를 연다. argv 가 실제로 `ha_repl` 이라 말하고 읽을 수 있는 conf 를 가리키는
프로세스만 집어온다 — **런을 지어낸 감시자는 절대 차오르지 않는 레인을 그리게 되기 때문이다.**

시나리오가 페어를 끊고 **움직인 토폴로지**에 같은 질문을 던질 수 있다. 그것으로 측정된 것은
[`evidence/ha/split-brain-divergence-converges.md`](../../project/evidence/ha/split-brain-divergence-converges.md)
에 있다.
