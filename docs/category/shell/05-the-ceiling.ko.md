## 상한이란 무엇인가

예약이 아니라 상한이다. tmpfs 는 거기에 쓰인 만큼만 차지하고 그 이상은 아니므로, 넉넉한 상한은
쓰이기 전까지 아무 비용도 들지 않는다.

```
   RAM
   ├──────────────────────────────────────────────────────────┤
   │                                                          │
   │  scenario_ram_mb           슬롯 × ~175 MB       나머지   │
   │  ┌────────────────────┐   ┌───────────────┐              │
   │  │ 코퍼스 오버레이    │   │ 슬롯마다      │              │
   │  │ 상위 층            │   │ CUBRID 서버   │              │
   │  │                    │   │ 하나          │              │
   │  │ ░░░░░░░░           │   └───────────────┘              │
   │  │ ▲       ▲          │                                  │
   │  │ 사용 중 high_water │   ← 새 케이스는 여기서 멈춘다 …  │
   │  └────────────────────┘    … 이미 도는 것은 멈추지 않는다│
   └──────────────────────────────────────────────────────────┘
```

그것이 하는 일은 *치우지 않는 케이스가 머신을 죽인다* 를 *공간이 없어 케이스 하나가 실패한다*
로 바꾸는 것이다.

## 런을 죽이는 세 가지 방식

크기를 잘못 잡으면 세 가지 방식으로 실패하고, 그것들은 전혀 닮지 않았다:

| 크기 | 무슨 일이 벌어지는가 | 무엇이 보이는가 |
|---|---|---|
| **RAM 에 비해 너무 큼** | 상한에 서버들을 더한 것이 메모리를 넘는다 | **OOM killer** 가 런을 가져가고, 런 자신의 로그에는 왜인지 말해주는 것이 아무것도 없다 |
| **너무 작음** | 케이스가 공간을 다 쓴다 | **ENOSPC**, 틀린 답을 낸 케이스와 정확히 똑같이 실패한다 |
| **간신히 아래** | 여유 없이 살아남는다 | 판정은 맞고, 자라는 코퍼스를 위한 자리는 없다 |

두 번째가 위험한 것이다. 출력의 무엇도 *이 케이스가 깨졌다* 와 *이 케이스는 쓸 곳이 없었다* 를
구별해주지 않기 때문이다. 그래서 자기 상한의 10% 안까지 간 런은 나가는 길에 **자기 판정이 쓸 수
없다고 선언한다.**

## 게이트가 왜 구해주지 않는가

`scenario_ram_high_water` 는 **새** 케이스를 붙잡는다. 이미 돌고 있는 것들이 나머지를 채우고,
실제로 그렇게 한다:

```
   t0   80% 게이트 ───────────────────────  슬롯 8 개 시작, 무거운 케이스 8 개
   t1   ░░░░░░░░░░░░░░░░ 60%                아직 끝난 것이 없다
   t2   ░░░░░░░░░░░░░░░░░░░░ 80%  ← 게이트  새 케이스는 시작하지 않는다
   t3   ░░░░░░░░░░░░░░░░░░░░░░░░ 100%       이미 돌고 있던 여덟이 거기까지 갔다
```

게이트는 구조상 늦다 — 다음 케이스를 멈출 수 있을 뿐, 이미 떠 있는 것은 결코 멈추지 못한다 —
그것이 `heavy_in_flight_max` 가 그 옆에 있는 이유다. `HeavyCap` 은 *시작* 에 관한 것이고, 그
지점에서는 아직 쓰인 것이 없고 모든 슬롯이 한꺼번에 비어 있으므로 피드백 규칙이 도울 수 없다.

## 크기 재기

```bash
CUBRID=/path/to/install scripts/sizing.sh
```

그것은 머신과 엔진 자신의 설정을 읽고 무엇이 슬롯 수를 묶는지 — 메모리, 코어, 디스크 — 그리고
모든 숫자가 무엇에 기대고 있는지를 말한다. 동의하지 않는 운영자가 그것이 어느 측정에서 왔는지
볼 수 있도록.

그것이 담고 있는 규칙 둘:

1. **상한에 서버들을 더한 것이 RAM 에 들어맞아야 한다.** `scenario_ram_mb + slots × 175 MB` 가
   `MemAvailable` 을 넘으면 런이 경고한다. 슬롯당 175 MB 는 예측이 아니라 예비다: 케이스 자신의
   작업 집합은 그보다 크고 미리 알 수 없다.
2. **크기 계산은 음수로 나올 수 있다.** 30 GB 머신에서는 어떤 상한도 슬롯 24 개에 맞지 않는다.
   그것은 우회할 무엇이 아니라 발견이다 — 정직한 선택지는 슬롯을 줄이거나 RAM 을 늘리는 것이다.

## `cubrid.conf` 은 판정에 중립적이지 않다

`db_volume_size` 와 `log_volume_size` 를 낮추는 것이 많은 슬롯을 tmpfs 안에 들어맞게 하는
것이다: 출하값 512 MB 에서는 케이스 하나가 행 하나를 쓰기도 전에 슬롯 여덟이 볼륨으로 8 GB 를
차지한다.

그러나 **일부 케이스는 출하값을 주장하고**, 그것을 낮추면 그 케이스들은 엔진이 아니라 런을 재게
된다. 부류가 둘이고, 읽어서 찾을 수 있는 것은 하나뿐이다:

**찾을 수 있는 것.** 파라미터를 찍는 케이스. 덤프는 `name=current (engine default)` 로 읽히고
괄호 없는 쪽만 `cubrid.conf` 에서 설정할 수 있으므로:

```
db_volume_size=512.0M (512.0M)   ← 현재 값을 고정한다. 영향 받음
db_volume_size=1.1G   (512.0M)   ← 자기 값을 설정한다. 영향 없음
```

자기 크기를 `cubrid_createdb` 에 넘기거나 `change_db_parameter` 로 설정하는 케이스는 영향을 받지
않는다. 코퍼스 전체에서 이 부류는 케이스 하나다.

**찾을 수 없는 것.** 크기를 한 번도 대지 않으면서 *동작* 에 의존하는 케이스 — 이를테면 임시
볼륨을 세는데 볼륨 크기가 바뀌면 그 수가 바뀌는 경우. 어떤 검색도 이 부류를 찾지 못한다;
코퍼스를 두 값으로 돌려 판정을 diff 해야만 찾아진다.

케이스가 출하값을 필요로 하는 곳에서는, 그 케이스 하나에 대해서만 그것을 되돌리는 패치가
해법이다:

```bash
# 패치 안에서, 케이스 자신의 본문 앞에
sed -i '/^[[:space:]]*db_volume_size[[:space:]]*=/d;/^[[:space:]]*log_volume_size[[:space:]]*=/d' \
    $CUBRID/conf/cubrid.conf
```

`case_patch_dir` 이 그것을 오버레이 안으로 적용하고, `cubrid.conf` 은 케이스마다 그 전에
복원되므로 다른 무엇에도 닿지 않으며, 디스크의 코퍼스는 바뀌지 않는다. 패치 세트와 그 README 는
[cubrid-testkit-patches](https://github.com/cubrid-systems/cubrid-testkit-patches) 에 있고, 그것은
비공개다.
