# 6. 실패한 것을 남기기

*[English](06-keeping-what-failed.md) · 한국어*

[← shell 카테고리로](README.ko.md)

케이스를 실패시키고 아무것도 남기지 않은 런은 진단하려면 다시 돌려야 한다. 이 문서는 지금 무엇이

## 지금 있는 것

CTP 의 `do_check_more_errors` 는 케이스가 core 파일을 남겼을 때, 또는 `$CUBRID/log` 안의
`FATAL ERROR` 줄 수가 늘었을 때 스냅샷을 뜬다:

```
$CTP_ERROR_BACKUP_DIR/AUTO_<build_id>_<datetime>.tar.gz
   ├── CUBRID/       ← 설치본 전체
   ├── <case_dir>/
   └── init_path/
```

그 트리거에 기대기 전에 알아둘 값이 있는 것 둘:

- **평범한 NOK 은 아무것도 얻지 못한다.** 틀린 답이나 올라오지 않은 서버는 스냅샷을 전혀 남기지
  않는다 — 판정과 `feedback.log` 안의 콘솔 출력뿐이다.
- `SKIP_CHECK_FATAL_ERROR=TRUE` 는 그것을 끄지 않는다. 그것은 `||` 의 한쪽 팔이고 다른 팔은
  core 파일이 있으면 언제든 발화하므로, core 는 그것이 무엇이라 하든 스냅샷이 떠진다.

**목적지는 설정할 수 있고**(`CTP_ERROR_BACKUP_DIR`), 기계 전체를 끌 수도 있다
(`CTP_ERROR_BACKUP=off`). 기본값은 여전히 `~/ERROR_BACKUP` 이므로, 둘 다 설정하지 않은 런은 늘
그랬던 그대로 동작한다.

## 그것이 얼마를 치르는가

이 코퍼스와 이 빌드에서 측정한 값:

| | |
|---|---:|
| 스냅샷이 실패하는 케이스마다 복사하는 설치본 전체 | **748.8 MB** |
| 슬롯 오버레이의 상위 층 — 케이스 하나가 실제로 바꾼 전부 | **~630 KB** |
| 케이스의 서버 로그만(`log/server/*.err`, `.event`, `.access`) | **~5 KB** |
| 브로커의 SQL 로그, 로그 트리의 99.6% | **MB 단위, 그리고 편차가 크다** |

실패가 일흔 개인 런은 홈 디렉터리에 수십 기가바이트를 쓰고, 그것을 측정 *안에서* 쓴다 — wall
clock 이 그것을 지고 가는데 출력의 무엇도 그렇다고 말하지 않는다.

## 설계: 설치본이 아니라 델타를 남긴다

설치본은 한 런의 모든 케이스에 대해 동일하다. 실패하는 케이스마다 그것을 복사하는 것은 같은
바이트 748 MB 를 거듭 복사하는 일이다.

**델타는 구조상 이미 분리돼 있다.** 각 슬롯은 하위 층이 깨끗한 설치본이고 상위 층이 케이스가 쓴
전부인 오버레이 뒤에서 돈다. diff 할 것도 없고 제외할 것도 없다 — 상위 층이 *곧* 답이다:

```
   하위 층                          상위 층
   ───────                          ───────
   $CUBRID  (748.8 MB)              이 케이스가 바꾼 전부  (~630 KB)
   bin/ lib/ share/ java/           log/*.err  log/server/*  log/pl/*
   jdbc/ msg/ demo/ timezones/      databases/  var/  케이스가 남긴 그대로의 conf/
   출하된 그대로의 conf/
        ▲                                ▲
        │                                │
   케이스마다 동일하다.             1,200× 작고, 무슨 일이 있었는지
   절대 복사하지 마라.              말해주는 부분이다.
```

앞의 스냅샷이 노리던 것은 전부 거기에 있다 — 서버의 `.err` 과 `.event` 로그, 유틸리티 로그,
케이스가 남긴 그대로의 `cubrid.conf`, 그리고 케이스가 아직 갖고 있었다면 데이터베이스까지.

core 파일은 예외다: 크고, 스택 트레이스가 필요로 하는 유일한 것이며, 이 티어에 접혀 들어가는
대신 자기만의 티어를 가질 값이 있다.

## 세 티어

티어의 경계는 판정이 아니라 **파일의 부류** 다. 값싼 티어는 *통과한* 케이스에 대해서도 남길 값이
있기 때문에 이것이 중요하다:

- CTP 는 NOK 을 쓸 때만 서버 로그에서 `Internal Error` 를 grep 하므로, 로그에 내부 오류가 있는
  채로 통과한 케이스는 그것에 대해 아무 말도 하지 않는다.
- 간헐적으로 실패하는 케이스는 실패만으로는 진단할 수 없다 — 통과한 런이 비교의 절반이다.
- 판정을 결코 바꾸지 않는 경고가 엔진 회귀가 처음 드러나는 방식이다.

| 티어 | 무엇 | 언제 | 3,444 케이스에 대한 비용 |
|---|---|---|---|
| **1. 항상** | `log/server/*`, `log/*.err`, `cubrid_utility.log`, 그리고 케이스가 자기 디렉터리에 쓴 것 | 통과든 실패든 모든 케이스 | **~15 MB 에 케이스당 몇 KB** |
| **2. 실패 시** | 브로커의 SQL 로그, 그리고 케이스가 남긴 그대로의 `cubrid.conf` | NOK | 케이스당 MB 단위, 상한 있음 |
| **3. 요청 시** | core 파일, 그리고 요청하면 데이터베이스 | core, 또는 명시적으로 | GB |

티어 1 에는 정책이 필요 없다. 기가바이트로 재는 tmpfs 에 대고 15 메가바이트는 반올림 오차이므로,
그것을 남길지 말지는 물을 값이 없는 질문이다.

**케이스 자신의 파일은 티어 2 가 아니라 티어 1 에 있고**, 그 경계는 그것이 방해가 된 뒤에
옮겨졌다. 그것이 실제로 무슨 일이 있었는지 말해주는 것이고 -- `exp.log`, `load.log`, diff --
킬로바이트 단위다. 그것을 판정 뒤에 두는 것은 이 문서가 주장하는 그 비교를 불가능하게 만들었다:
어떤 머신에서는 통과하고 다른 머신에서는 실패하는 expect 케이스 둘을 진단할 수 없었는데, 통과한
런이 견줄 것을 아무것도 남기지 않았기 때문이다. 빠져 있던 1,979 바이트를 되찾는 데 런 하나가
들었다. 브로커 로그는 판정 뒤에 남는다, 그것이 메가바이트이기 때문이다.

## 어디로 가는가

```
$CTP_HOME/result/<category>/
  current_runtime_logs/       ← 동결. 건드리지 않는다
  case-logs/                  ← 이 러너 자신의 것, patched.txt 처럼
    _06_issues/_14_1h/bug_a/cases/
      server/                 ← 티어 1: log/server/*
      pl/                     ← 티어 1
      *.err                   ← 티어 1: log/*.err, cubrid_utility.log
      broker/                 ← 티어 2, 실패 시
      cubrid.conf             ← 티어 2: 케이스가 남긴 그대로
```

경로는 **코퍼스가 이름 붙인 그대로의** 케이스다 — 앞에서 시나리오를 떼고 뒤에서 `<name>.sh` 를
뗀 것인데, `<name>/cases/<name>.sh` 가 자기를 되풀이하기 때문이다. 대신 절대 경로를 남기면 모든
캡처가 코퍼스가 마침 체크아웃돼 있던 곳의 사본 아래에 묻히는데, 그것이 첫 구현이 한 일이고 지금은
테스트가 막는 일이다.

**타임스탬프가 아니라 케이스 경로로 이름 붙인다.** CTP 의 `AUTO_<build>_<datetime>` 은 한 번에
케이스 하나가 돌 때는 모호하지 않고 여덟에서는 그렇지 않게 된다 — tarball 여럿이 같은 초에
떨어지는데 이름은 어느 케이스가 어느 것에 있는지 말해주지 않는다. 케이스 경로는 구조상
유일하므로 할당하거나 중복을 풀 것이 없다. 재시도는 `<case path>/try2/` 가 된다.

`~/ERROR_BACKUP` 은 자기 트리거와 자기 내용을 그대로 유지한다. 그것은 다른 질문에 답한다 —
*core 를 포함해 전부 달라* — 그리고 성공한 케이스의 로그를 ERROR_BACKUP 이라는 이름의 디렉터리
아래에 두면 그 이름이 거짓이 되고 그것을 읽는 무엇이든 깨진다.

## 캡처 지점, 그리고 그것이 하면 안 되는 일

캡처는 **판정 뒤, 슬롯 리셋 전** 에 일어나야 한다. 리셋(`RestoreScript`)은 케이스의 끝이 아니라
*시작* 에 돌기 때문에, 케이스가 쓴 것은 다음 케이스가 그 슬롯을 가져갈 때까지 살아남는다 —
그리고 `dropInSlot` 은 한 디렉터리의 마지막 케이스가 끝나면 코퍼스 오버레이를 버린다. 판정
전에는 남길 것이 없고, 그 둘 중 어느 쪽 뒤에도 복사할 것이 남아 있지 않다.

**그리고 런이 끝나면 슬롯들은 간다.** 그 상위 층은 런의 슬롯 루트와 함께 지워지므로, 각 슬롯의
마지막 케이스도 `$CUBRID` 에 남긴 것을 잃는다. 런 뒤에 케이스가 쓴 것은 복사된 곳에서만
살아남는다: `case-logs/`, 그리고 그 백업이 켜져 있는 동안 core 를 남기거나 치명적 오류를 기록한
케이스에 대해서는 `~/ERROR_BACKUP`. 상위 층은 예전에는 `/var/tmp/testkit-slots/<pid>` 아래에서
런보다 오래 살아남았는데, 같은 pid 를 가진 나중의 런이 그 위에 마운트하고 그것들이 담고 있던
것에서 시작할 때까지 그랬다.

그것은 슬롯의 오버레이 상위 층을 바깥에서 읽는 대신 **경로로, 케이스 자신의 통로를 통해**
복사한다. 어느 쪽이든 같은 파일이고, 런이 오버레이를 갖고 있든 슬롯 하나든 둘 다 아니든 똑같이
동작한다. 목적지는 어떤 슬롯도 오버레이하지 않는 `CTP_HOME` 아래이므로, 슬롯 안에서 만들어진
사본은 진짜 파일시스템에 떨어지고 슬롯보다 오래 산다.

규칙 둘:

- **복사하고, 절대 옮기지 마라.** 케이스는 여전히 자기 판정에 대한 진실의 원천이다.
- **실패한 캡처가 케이스를 실패시켜서는 안 된다.** 진단하고 있는 대상을 바꾸는 진단은 진단이
  없는 것보다 나쁘다. 캡처가 일어나지 않았다고 기록하고 계속 가라.

그리고 단서 하나: 원본은 흔히 tmpfs 인데 목적지는 디스크이므로, 티어 2 는 회수 경로에 I/O 를
더한다. 티어 1 의 15 메가바이트는 잴 값이 없고, 티어 2 의 것은 있다.

## 설정

| | 기본값 | |
|---|---|---|
| `case_logs` | `off` | `off`, `fail`, 또는 `all` — `all` 은 통과한 케이스에 대해서도 티어 1 을 남긴다. 셋 중 어느 것도 아닌 모드는 `off` 로 읽히지 않고 거부된다 |
| `case_logs_max_mb` | — | 런 전체에 대한 예산; 거기 닿으면 캡처가 멈추고 그렇다고 한 번 말한다 |
| `CTP_ERROR_BACKUP` | 켬 | `off` 는 무거운 스냅샷을 통째로 끈다 |
| `CTP_ERROR_BACKUP_DIR` | `~/ERROR_BACKUP` | 무거운 스냅샷이 가는 곳 |

기본이 `off` 인 것은 기능이 새것이고, 그것을 한 번도 요청한 적 없는 런이 요청하지 않은
메가바이트를 쓰기 시작해서는 안 되기 때문이다. 티어 1 은 코퍼스 전체에 대해 15 MB 로 측정됐으므로
나중에 `all` 을 기본값으로 삼는 것도 변호할 수 있다; 그것은 논쟁이 아니라 회수 경로 비용을
측정해서 정해야 한다.

```
case_logs=all
case_logs_max_mb=512
```


## 구현이 지키는 규칙 둘

**실패한 캡처는 케이스를 실패시키지 않는다.** 모든 복사는 `2>/dev/null` 이고 스크립트는 무슨 일이
있었든 0 으로 끝난다; 아예 돌 수 없었던 캡처는 `[WARN]` 줄로 보고되고 케이스는 자기 판정을
지킨다. 진단하고 있는 대상을 바꾸는 진단은 진단이 없는 것보다 나쁘다.

**예산을 넘긴 캡처는 남고, 그것이 마지막이다.** 이미 쓰인 뒤에 그것을 거부하면 런은 비용을
치르고도 버린 셈이 되므로, 예산은 이것을 버리는 대신 *다음* 캡처를 멈춘다 — 그리고 런은
케이스마다가 아니라 한 번 그렇게 말한다.

---

이것을 만들게 한 사례를 정직하게 적어둔다: 스물두 케이스 중 열아홉이 `cubrid server start: fail`
을 보고한 런을 진단할 수 없었는데, 왜인지 설명하는 서버 자신의 `.err` 파일이 이미 버려진 오버레이
안에 있었기 때문이다. 이것이 막으려고 존재하는 것이 그것이다.
