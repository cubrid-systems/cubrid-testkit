## 단계들

CTP 의 `sql/bin/run.sh` 는 여섯 단계가 줄지어 있는 것이고, 이 러너도 같은 여섯이다. 앞의 셋과
마지막은 셸이고 — 스크립트는 CTP 의 것을, diff 할 수 있을 만큼 가깝게 옮긴 것이다 — 네 번째는
Go 다.

| 단계 | 무엇을 하는가 |
|---|---|
| `do_init` | 데이터베이스의 이름(`basic`, medium 이면 `mdb`)과 카테고리 |
| `do_clean` | 데이터베이스를 멈추고 지우고, 이 사용자의 `cub` 프로세스를 죽이고, 그 공유 메모리를 없앤다 |
| `do_configure` | conf 의 `[sql/cubrid.conf]` 과 브로커 섹션들을 엔진 자신의 파일에 쓰고, 11.5 이상에서 sql 에는 `en_US.utf8` 을 강제한다 |
| `do_create_db` | `createdb`, 로케일, 그리고 데이터: sql 은 저장 프로시저를 컴파일해 적재하고, medium 은 `mdb.tar.gz` 을 풀어 적재한다 |
| `do_test` | 케이스들 — [실행기](#실행기), 그리고 그 주위 전부는 Go |
| `do_summary_and_clean` | 요약 파일들, core 파일 찾기, 그리고 정리 |

앞의 셋은 어떤 슬롯이 있기도 전에, 러너 자신의 네임스페이스 안에서 한 번 돈다. 그것들이 만드는
데이터베이스는 `$CUBRID/databases/<db>` 에 있고 그것은 `$CUBRID` 안이다 — 그래서 모든 슬롯의
오버레이가 그것을 하위 층으로 갖는다. 한 번 준비되고, 복사되는 일은 없고, 모든 슬롯에서 같은
경로에 있으므로 `databases.txt` 안의 무엇도 다시 쓸 필요가 없다.

`do_clean` 은 지운다. 그것이 지우는 경로들 — `$CUBRID`, `$CTP_HOME`, 시나리오 — 은 돌기 전에
점검된다: 셸 스크립트에서 설정되지 않은 경로는 오류가 아니라 파일시스템의 루트이고, shell 쪽의
어떤 런은 변수 하나가 비어 있었다는 이유로 머신 전체에서 디렉터리 69 개를 지운 적이 있다.

## 실행기

케이스는 CQT — CTP 가 늘 써온 Java — 가 실행하고, 다른 무엇도 아니다. 다시 쓰인 것은 그 둘레의
루프다: 발견, 제외 파일, 케이스가 어느 답과 견주어지는지, 비교, 그리고 런이 쓰는 모든 파일.

그 분할이 [ADR-016](../../project/adr/ADR-016-sql-executor.md) 이다. 그것이 있는 이유는 `.sql`
케이스가 텍스트를 만들어내는 스크립트가 아니기 때문이다; 그것은 파서와 연결과 렌더러와, 오직
CQT 자신의 코드만이 정확히 맞히는 오류·힌트 규칙 묶음이 만들어낸 텍스트다. 그것들을 다시 쓰는
일은 영원히 바이트 단위로 같게 유지해야 할 두 번째 구현을 갖는 일이 된다.

그래서 각 슬롯은 런 전체에 대해 JVM 하나를 띄우고 — `TestkitExecutor`, 루프가 없는 CQT —
러너는 거기에 케이스를 하나씩 건넨다:

```
   러너 ──"X <case>"──►  JVM          stdout 이 아니라 fd 3 으로: 스레드 덤프나
        ◄─"R <bytes> <ms>"─           JVM 로그 한 줄이 stdout 에 나오면 이후의
                                      모든 판정이 하나씩 밀린다
```

JVM 은 함께 도는 CTP 에 맞춰 컴파일되고, 리플렉션으로 닿는 모든 클래스는 준비됐다고 말하기
전에 조회되며, 빠져나오는 것은 무엇이든 대답도 종료도 하지 않는 JVM 이 아니라 오류와 종료가
된다.

CQT 가 제 나름대로 케이스에서 케이스로 들고 가는 것이 하나 있다: server-message 플래그다.
`--+ server-message` 힌트가 그것을 켜고, 그것이 오류가 자기 코드 아래에 메시지를 찍을지를
정한다. 슬롯 런에서는 주어진 케이스 앞의 케이스들이 CTP 의 것이 아니므로, 각 실행기는 케이스마다
그 전에 CTP 의 단일 런이라면 그 플래그를 어디에 두었을지를 듣고, CQT 자신의 코드를 통해 그것을
거기에 둔다.

## 여기서 슬롯이란 무엇인가

슬롯은 shell 스위트의 슬롯과 같은 것이다 — 프로세스, 공유 메모리, 네트워크, 마운트를 위한
네임스페이스 — 여기에 이 계열에 속한 것 둘이 더해진다:

- **`$CUBRID` 는 오버레이 뒤에 있다.** 하위 층은 준비된 데이터베이스가 들어 있는 설치본이고,
  슬롯이 쓰는 모든 것은 자기 상위 층에 떨어져 끝에 버려진다. 그래서 모든 슬롯이 미리 슬롯마다
  1 GB 를 복사하지 않고도 같은 데이터베이스를 돌린다.
- **디렉터리는 통째로 가져간다.** `dispatch.Queue.Affinity` 가 디렉터리를 그 첫 케이스를
  가져간 슬롯에게 주고, 디렉터리의 나머지가 따라간다. 한 디렉터리의 케이스들은 이웃이 남긴 것에
  의존한다: 각 디렉터리 안의 순서를 뒤집으면 medium 의 975 케이스 중 71 개가 실패하고, 그중
  62 개는 한 사슬에 있다.

슬롯 하나에 격리 없이 도는 런은 CTP 가 그러듯 머신 자체에서 돈다.

## 런이 무엇을 쓰는가

이 프로그램 바깥의 독자나 스크립트가 볼 수 있는 것은 전부 CQT 의 것이고 바이트 단위로 같다 —
진행 줄들, 케이스마다 그 옆에 놓이는 `.result`, 실패 복사본들, 그리고 결과 트리:

```
$CTP_HOME/sql/result/y2026/m9/schedule_linux_sql_64bit_<ddHHmmss><rnd>_<build>/
├── main.info              집계, 빌드, 머신
├── summary.info           같은 것의 XStream 트리
├── summary.xml            모든 케이스, 그 답, 소요시간, 판정
├── linux_sql_64bit.xml    JUnit 리포트
└── sql/…/summary_info     디렉터리마다: 합계, 그리고 케이스마다 한 줄
```

그 파일들 안의 순서 둘은 누구의 선택이 아니라 Java 의 컬렉션이고 — `summary_info` 의 자식들과
JUnit 리포트의 케이스들은 런의 타임스탬프를 담은 경로에 대한 JDK 8 `Hashtable` 순회를 따른다 —
그것들은 재현된다. CTP 와의 비교는 바이트의 비교이기 때문이다.
[`sql/records.sh`](../../project/evidence/sql/records.sh) 가 그것을 실제 CTP 런과 견주어
점검한다.

러너 자신의 출력은 표준 오류로 가고 표준 출력으로는 절대 가지 않는다: CTP 가 거기 찍는 것은
동결돼 있고 비교되기 때문이다.
