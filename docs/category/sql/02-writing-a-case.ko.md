## 배치

케이스는 SQL 파일 하나와 기대 텍스트 파일 하나이고, 형제 디렉터리에 놓인다:

```
sql/_13_issues/_26_1h/
├── cases/cbrd_26541.sql       문장들
└── answers/cbrd_26541.answer  그것을 돌려서 나온 것
```

이름이 일치하고, 확장자는 `.sql` 이며, `cases/` 안의 다른 무엇도 케이스가 아니다 — `.txt`
헬퍼는 무시되고, `answers/` 와 `common/` 은 케이스를 찾느라 훑지도 않는다. 디렉터리는 슬롯이
가져가는 단위이고, 그래서 디렉터리는 그 안의 케이스들이 서로에게 기대도 되는 단위이기도 하다.

## 복사해서 쓸 수 있는 케이스

```sql
--+ holdcas on;
--[er]length() of an attribute that does not exist

create table t_demo (b varchar(10));
insert into t_demo values ('22');

select length(b) from t_demo;
select length(no_such_attribute) from t_demo;

drop table t_demo;
--+ holdcas off;
```

그 안의 세 가지는 문법이 아니라 관례다: 본문을 감싸는 `--+ holdcas on` … `off`, 6,821 개
케이스가 쓴다; 케이스가 무엇을 위한 것인지 말하는 첫 줄 주석, 케이스의 요점이 오류일 때는
`[er]` 를 붙인다(2,911 개 케이스가 그렇게 한다); 그리고 이슈 id 가 있다면 그것을 이름으로 쓰는
것.

## 답은 어디서 오는가

**케이스를 돌려서 나온 것을 남겨라.** 답을 손으로 쓰지 마라: 렌더링에는 모양이 있고 — 구분자,
헤더, 값의 정확한 간격, 실패한 문장에 대한 `Error:-<code>` — 손으로 쓴 파일은 시험하려는 동작과
아무 상관 없는 방식으로 달라진다.

```bash
mkdir -p /tmp/mycorpus/_99_mine/{cases,answers}
cp t_demo.sql /tmp/mycorpus/_99_mine/cases/
: > /tmp/mycorpus/_99_mine/answers/t_demo.answer     # 비어 있다: 이 케이스는 일부러 실패한다

sed 's#^scenario=.*#scenario=/tmp/mycorpus#' sql.conf > /tmp/mycase.conf
TESTKIT_NATIVE=sql TESTKIT_CONTAIN=1 testkit sql -c /tmp/mycase.conf

cp /tmp/mycorpus/_99_mine/cases/t_demo.result /tmp/mycorpus/_99_mine/answers/t_demo.answer
```

두 번째 런은 통과하고, 그 답은 이 코퍼스에 대한 이 엔진의 기록이다. 남기기 전에 읽어라: 답은 그
케이스가 영원히 주장할 것이고, 그 안에 케이스가 주장하려던 것이 아닌 무엇 — 행 순서, 플랜, 다른
케이스가 일으킨 오류 — 이 있다면 그것은 일을 다른 순서로 하는 머신을 기다리는 실패다.

CQT 에는 답을 대신 써주는 모드가 실제로 있지만, CTP 의 진입점은 거기에 닿지 않는다: 에이전트가
result 모드를 설정하고 다른 쪽을 내주는 것은 없다. `.result` 를 가져가는 것이 지원되는 방법이다.

## 렌더링은 어떻게 생겼는가

위의 케이스를 돌리면 나오는 것:

```
===================================================
0
===================================================
1
===================================================
char_length(b)    
2     

===================================================
Error:-494
===================================================
0
```

- 각 문장의 출력 앞에 `=` 쉰한 개짜리 줄 하나;
- 행을 돌려주지 않는 문장 — `create` 와 `drop` — 에는 `0`, 그리고 insert 가 건드린 행의 수;
- 질의에는 컬럼 이름들 다음에 행들, 값마다 그 뒤에 공백 다섯 개, 마지막 행 뒤에 빈 줄 하나.
  헤더는 쓰인 그대로의 표현식이므로 `length(b)` 는 `char_length(b)` 로 돌아온다: 답은 케이스의
  이름이 아니라 엔진의 이름을 기록한다;
- 문장이 실패하면 `Error:-<code>`. 그 아래의 메시지는 `--+ server-message on` 힌트가 요청했을
  때만 나온다.

비교는 양쪽에서 `\r` 과 `\n` 을 모두 걷어낸 뒤 같기를 요구한다. 그래서 줄이 어디서 나뉘는지는
주장되지 않고, 빈 줄도 마찬가지다 — 그러나 나머지 전부는 주장된다: 값 뒤에 붙은 공백, 그리고
행이 돌아온 순서.

## 코퍼스가 쓰는 프라그마들

매뉴얼에서 나열한 것이 아니라 이 코퍼스에서 센 것이다:

| | 쓰임 | |
|---|---:|---|
| `--+ holdcas on` / `off` | 6,821 | 문장들에 걸쳐 연결의 트랜잭션을 열어둔다; 관용은 케이스를 감싸는 것이다 |
| `--+ server-message on` / `off` | 2,559 | 오류의 메시지를 그 코드 아래에 찍는다. **무언가 끄기 전까지 켜져 있고**, 그래서 슬롯 런은 케이스마다 그 전에 CTP 의 순서라면 있었을 자리로 그것을 되돌린다 |
| `evaluate '<text>'` | 2,924 | 출력에 라벨을 써넣어, 긴 케이스가 각 블록이 어느 단계에 속하는지 말하게 한다 |
| `--@queryplan` | 586 | 문장의 플랜을 출력에 덧붙인다 |
| `--@fullplan` · `--@joingraph` | 10 · 2 | 같은 것이 더 있지만, 드물다 |
| `$<type>, $<value>, …`, 문장 앞줄에 | 1,000+ | 그 안의 `?` 에 바인딩할 값들, 타입이 먼저: `$varchar, $1, $varchar, $json_array('aa')` |

`@conn:` 은 CTP 의 파서에는 나오지만 **이 코퍼스의 어떤 케이스에도** 나오지 않으므로, 여기서
그것에 의존하는 것은 없다.

## 다른 조건을 위한 답들

케이스는 답을 여럿 가질 수 있고, 런은 설정된 모드와 데이터베이스의 charset·collation 으로
고른다:

```
answers/1001.answer                         기본값
answers/1001.answer_cci                     이런 것이 335 개: CCI 드라이버는 다르게 렌더링한다
answers/1001.answer_D_utf8_C_utf8_bin       데이터베이스의 charset 과 collation
```

그런 파일이 2,423 개 있다. 런이 어느 것을 쓰는지는 `jdbc_config_file` 이 가리키는 XML 의
`<run_mode>` 요소에서 온다 — 그리고 그 요소가 없으면 런은 평범한 `.answer` 를 쓴다.

## 케이스가 따라야 할 규칙들

이것은 스타일이 아니다: 하나하나가 앞선 케이스들이 바뀔 때 케이스를 실패시키는, 측정된
원인이다.

- **만든 것은 치워라.** 이 코퍼스의 1,922 개 케이스가 테이블을 만들고 한 번도 drop 하지 않으며,
  그 이름 중 245 개는 둘 이상의 디렉터리가 만든다 — `t1` 은 61 개 디렉터리가 남기고 423 개가
  만든다. 자기가 만든 것을 drop 하는 케이스는 다른 케이스가 실패하는 이유가 될 수 없다.
- **필요한 것은 만들고, 이름이 흔하면 먼저 drop 하라.** 맨 위의 `drop table if exists t1;` 은
  출력 한 줄을 치르고 실패 한 부류를 통째로 없앤다.
- **읽는 것은 순서를 정하라.** `ORDER BY` 가 없는 카탈로그 `select` 는 카탈로그가 마침 갖고 있는
  순서로 행을 돌려주고, 그것은 앞서 만들어진 모든 것에 달려 있다. 순서를 완전히 결정하는 것으로
  정렬하라 — 인덱스 목록이라면 키의 위치까지 포함해서.
- **바꾼 것은 되돌려라.** `set system parameters` 는 연결에 살고, 세션 변수도 그렇다 — CUBRID 는
  그것을 **스무** 개 갖고 있으므로, 다섯 개를 남기는 케이스는 다음 케이스의 예산을 쓴다. 끝에서
  변수를 drop 하고 파라미터를 복원하라.
- **자기 것이 아닌 것을 읽지 마라.** `_db_user` 목록에는 다른 케이스가 어떤 사용자에게
  비밀번호를 주었는지가 들어 있고, trace 는 서버 자신의 질의를 보여준다. 케이스가 select 하는
  범위를 케이스가 만든 것으로 한정하라.

다섯 가지를 모두 따르는 케이스는 앞에 무엇이 돌았든 같게 돈다 — 그것이 코퍼스를 병렬화할 수
있게 만드는 것이다. 코퍼스가 그것을 따르지 않는 곳에서는, 상류가 받아줄 때까지
[패치](06-when-a-case-fails.ko.md#패치로-코퍼스-수정-옮기기)가 그 수정을 들고 간다.
