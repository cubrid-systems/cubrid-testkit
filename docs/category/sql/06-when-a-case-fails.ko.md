## 판정이란 무엇인가

케이스는 문장들이 담긴 파일이다. CQT 는 그것을 연결 하나 위에서 돌리고 그 결과 — 행들, 컬럼
헤더, 오류 코드 — 를 `=` 쉰한 개짜리 줄로 나뉜 텍스트로 렌더링한다. 그 텍스트는 케이스 옆에
`<name>.result` 로 쓰이고, 양쪽에서 캐리지 리턴과 개행을 걷어낸 뒤 `answers/<name>.answer` 와
비교된다. 같으면 케이스는 OK 다.

붙들어둘 값이 있는 귀결 둘:

- **답은 주장이 아니라 기록이다.** 그것은 어떤 엔진에 대고 이 코퍼스를 돌려서 나온 것이고, 그
  런이 만들어낸 것을 무엇이든 담고 있다 — 목록의 행 순서, 플랜, 그리고 남겨진 객체가 일으킨
  오류까지.
- **답이 없는 케이스는 세어지고 절대 돌지 않는다.** CQT 는 그것을 목록과 `N` 안에 두면서
  실행하지는 않고, 그 요약은 그것을 어느 열에서도 세지 않는다 — 그래서 `Total` 은
  `Success + Fail` 이 아니고, `main.info` 의 `execute_case` 가 그 둘을 더한 것이다.

## 어디를 볼 것인가

```
cubrid-testcases/sql/<family>/cases/<name>.result     이 런이 만들어낸 것
cubrid-testcases/sql/<family>/answers/<name>.answer   그것이 견주어지는 것
$CTP_HOME/sql/result/…/sql/<family>/<name>.result     복사본, 실패했기에 남겨진 것
$CTP_HOME/sql/result/…/sql/<family>/<name>.answer     그 옆의 답
$CTP_HOME/sql/result/…/sql/<family>/<name>.err        케이스가 core 를 남겼다면, gdb 의 스택
$CTP_HOME/sql/result/…/summary.xml                    모든 케이스, 소요시간, 판정
```

결과 트리 안의 그 쌍을 `diff` 하라: 그 둘은 이 런 자신의 것이고, 코퍼스 안의 쌍은 다음 런이
덮어쓴다.

상태 페이지(`status_http=on`)가 런이 도는 동안 같은 질문에 답한다: 실패하는 케이스는 result 가
answer 에서 벗어나는 첫 줄을 그 주변 줄들과 함께 보여준다.

### core 를 남긴 케이스

케이스가 실패한 뒤 런은 `$CUBRID` 아래에서 `core.<digits>` 를 찾고, 전에 본 적 없는 core 는 그
케이스의 것이다. 그러고 나서 `gdb` 에 `bt full` 을 요청하고 그 답을 실패 복사본들 옆에
`<name>.err` 로 쓴다:

```
SUMMARY:
CORE_DIR:/home/q/CUBRID
core.410914 [cub_server] Core dumped in pt_check_where at src/parser/semantic_check.c:9814

==================core.410914==================
#0  0x00007f1f in __pthread_kill_implementation () from /lib/x86_64-linux-gnu/libc.so.6
…
```

한 줄 요약은 CUBRID 자신의 소스에서 가장 안쪽 프레임의 이름을 대고, 모든 크래시가 빠져나오는
길에 남기는 오류 처리 기계는 건너뛴다. 바이너리에 심볼이 없으면 그것은 비고, 헤더 줄은 프로그램
이름에서 끝난다.

알아둘 값이 있는 것이 둘이다. 분석은 런이 끝난 뒤가 아니라 케이스가 끝날 때, **core 가 있는 그
슬롯 안에서** 돈다 — 슬롯의 `$CUBRID` 와 core 를 남긴 `cub_server` 는 슬롯이 갈 때 함께 가기
때문이다. 그리고 core 를 하나라도 찾은 런은 마지막 정리를 건너뛰므로 core 들은 그 뒤에도 그대로
있다; 슬롯의 것은 그 오버레이가 버려지기 전에 `<result root>/slot_cores/` 로 복사돼 나온다.

## 엔진의 잘못이 아닌 실패들

직렬 런은 모든 케이스에게 CTP 의 런이 주었던 것과 같은 선행 케이스들을 준다. 슬롯 런은 그렇지
않고 — 앞선 케이스가 남긴 것을 읽은 케이스는 그것과 함께 판정을 바꾼다. 그것이 어떻게 보이는지:

| 무엇이 보이는가 | 그것이 무엇인가 |
|---|---|
| 답에는 결과가 있는 자리의 `Error:-494` | 케이스가, 다른 케이스가 남긴 이름의 테이블을 만들었다 |
| 답에는 없는 행이 카탈로그 목록에 있다 | 다른 케이스가 남긴 객체, 그리고 케이스 범위로 한정되지 않은 목록 |
| 같은 행들이 다른 순서로 | `ORDER BY` 가 없는 목록, 카탈로그의 내력이 정한 순서 |
| `-1071 Too many session variables` | CUBRID 는 연결당 스무 개를 갖고, 이 케이스 앞의 케이스들이 자기 것을 남겼다 |
| `Query Plan:` 이나 `Trace Statistics:` 블록이 없다 | trace 가 무엇을 찍는지는 서버의 상태에 달려 있고, 때로는 케이스가 통제하지 않는 무엇에도 달려 있다 |

측정값, 패치 세트를 적용했을 때: **슬롯 여섯 런마다 17,459 개 중 0 에서 2 개**, 같은 pin 에서
CTP 혼자 돌 때 런마다 0 에서 2 개인 것에 대해서. 고칠 수 있었던 계열은 고쳐졌고, 남은 것은
[지금 불안정한 것](#지금-불안정한-것)에 있다.

## 패치로 코퍼스 수정 옮기기

순서에 기대는 케이스는 고칠 값이 있는 케이스이고, 그 수정이 있을 자리는 상류다. 거기 닿기까지는
런이 그것을 들고 갈 수 있다:

```
[sql]
case_patch_dir=/path/to/cubrid-testkit-patches/sql
```

패치는 unified diff 이고 케이스마다 하나이며, 첫 케이스 전에 적용되고 끝에 되돌려진다 — 슬롯들은
코퍼스 하나를 공유하므로 모든 슬롯이 같은 소스를 읽어야 한다. 더 이상 적용되지 않는 패치는 런을
멈춘다. 그것은 케이스가 옮겨졌다는 뜻이고, 그것을 패치 없이 돌리는 것은 아무도 하지 않은 질문에
답하는 일이기 때문이다. 무엇이 패치됐는지는 결과 트리의 `patched.txt` 에 쓰이고, 표준 출력으로
알려지고, 페이지에 보인다: 패치된 소스에서 나온 판정은 패치된 케이스에 대한 주장이다.

그 하나하나의 뒤에 있는 원칙은 같다 — **케이스는 자기가 필요로 하는 것을 말하고 자기가 남기는
것을 치운다** — 그리고
[cubrid-testkit-patches](https://github.com/cubrid-systems/cubrid-testkit-patches)(비공개)의
README 가 각각이 무엇을 왜 하는지 말한다. 하나 쓰려면: 코퍼스 사본에서 케이스를 고치고, 돌리고,
손으로 쓰는 대신 그것이 만들어낸 `.result` 를 새 답으로 삼고, 케이스 디렉터리 기준 상대 경로로 두
파일을 diff 하라.

## 지금 불안정한 것

코퍼스 안에서는 고칠 수 없다고 알려진 것이 둘이고, 덮어두는 대신 적어둔다:

- **다른 누군가가 원하는 이름을 가진, 남겨진 테이블.** 1,922 개 케이스가 테이블을 만들고 한 번도
  drop 하지 않으며, 그 이름 중 245 개는 둘 이상의 디렉터리가 만들고, `t1` 하나만 해도 61 개
  디렉터리가 남기고 423 개가 만든다. 그것은 패치 세트가 아니라 코퍼스 전체의 규칙이다.
- **엔진이 늘 찍지는 않는 플랜을 가진 trace.** 케이스들은 이미 `recompile` 을 요청한다; 빠지는
  블록은 서버가 병렬화하거나 내부적으로 다시 쓰는 질의의 플랜이다. CTP 자신의 두 런이
  `cbrd_25542` 에 대해 서로 엇갈리고, 여기서의 직렬 런은 `cbrd_25708_eq_in` 에 대해 엇갈린다.

실패가 둘 중 어느 쪽으로 보이면, 그것을 회귀로 읽기 전에 두 번째 런과 비교하라.
[`project/evidence/regression-sql.md`](../../project/evidence/regression-sql.md) 가 같은 비교를
조심스럽게, 한쪽마다 두 번씩 해둔 것이다.
