# 슬롯 제공자, 선택적 volatile, 배치, 그리고 그 위의 한 층

- **날짜:** 2026-09-23
- **상태:** 설계. 구현 없음. 결정이 필요한 지점은 **결정 필요** 로 표시했다.
- **무엇인가:** 오늘 가능성 조사에서 "없음"으로 나온 셋과, 그것들이 무엇을 위해 필요한지에
  대한 설계. 셋은 따로 떨어진 항목이 아니라 **하나의 그림**이고, 그림의 꼭대기가 축 O 다.
- **읽기 전에:** [ADR-014](../adr/ADR-014-one-machine.md) (러너는 한 머신),
  [ADR-022](../adr/ADR-022-topology-provider.md) (토폴로지는 요청한다),
  [`contracts.md`](contracts.md) C3 (Channel),
  [`migration-exclusions.md`](../concept/migration-exclusions.md) §0 (축 분리).

---

## 0. 왜 넷이 한 문서인가

오늘의 조사는 네 개의 "없음"을 남겼다:

| | |
|---|---|
| 클러스터·노드 단위 선택적 volatile | csb |
| shell 이 슬롯 제공자를 고르는 것 | testkit |
| 노드를 어느 머신에 띄울지 | csb |
| 여러 머신에 일을 뿌리는 것 | **어디에도 아님 — 그게 요점** |

넷째가 앞의 셋을 설명한다. 케이스를 여러 머신에 뿌리려면 (a) 일을 담을 그릇이 머신을 가릴 수
있어야 하고 — 슬롯 제공자 — (b) 그릇이 다른 머신에 설 수 있어야 하고 — 배치 — (c) 그릇이 그
머신의 자원 안에 들어가야 한다 — volatile. 앞의 셋을 따로 만들면 넷째가 올 때 셋 다 모양이
안 맞는다.

## 1. 축을 다시 긋는다 — 금지된 것은 러너가 fleet 을 갖는 것이다

ADR-014 는 **러너**가 함대를 갖는 것을 금지했다. 그 이유는 측정이었다 — CTP 가 그렇게 쓰이지
않았다. 그러나 같은 문서가 fleet 을 *거부* 하지 않고 **유예** 했다:

> **The fleet is recorded as excluded and deferred:** the instance inventory, deployment across
> several machines, dispatching cases between them, and adding or removing a machine mid-run.

그리고 [`migration-exclusions.md`](../concept/migration-exclusions.md) §0 이 유예의 형태를
정해뒀다. 이것은 개별 판단이 아니라 프로젝트 전체의 방향성이라고 그 문서가 스스로 말한다:

> 이번 마이그레이션은 축 T 만 옮긴다. 축 O 는 제외하고, 제외했다는 사실을 여기에 남기고,
> **나중에 새로운 층으로 다시 세운다.**

**그래서 축 O 는 testkit 안에 생기는 기능이 아니라 testkit 위에 서는 층이다.** 이 구분이 이
문서 전체를 지배한다:

| | 소유 |
|---|---|
| 케이스를 고르고 · 돌리고 · 판정하고 · 파일로 남긴다 | **러너.** 한 머신. 바뀌지 않는다 |
| 무엇을 어디서 돌릴지 정하고 · 환경을 세우고 · 결과를 모은다 | **위의 층.** 여럿을 안다 |

러너는 자기가 여럿 중 하나라는 것을 **모른다.** 그것이 ADR-014 를 지키는 방법이고, 동시에
동등성 게이트를 지키는 방법이다 — 게이트는 두 러너의 파일을 비교하는데, 러너가 분배를 알게
되면 어느 차이가 러너의 것이고 어느 것이 분배의 것인지 한 겹이 더 생긴다.

## 2. 슬롯 제공자 — testkit 안의 이음매

### 2-1. 지금

슬롯은 `internal/contain` 하나다. `Enter` 가 `main` 의 첫 동작으로 user·mount·PID·IPC
네임스페이스를 만들고, `slot.go` 가 `$CUBRID`·시나리오·레지스트리 위에 오버레이를 얹는다.
**"슬롯을 무엇이 제공하는가"라는 질문 자체가 코드에 없다.** 그래서 두 번째 제공자를 붙일 자리가
없다.

### 2-2. 이음매가 무엇을 약속해야 하나

케이스가 전제하는 것이 곧 계약이다
([`category/shell/02-writing-a-case.md`](../../category/shell/02-writing-a-case.md) 의
"케이스가 전제해도 되는 것"이 이미 그 목록이다). 슬롯 제공자는 그 목록을 만족시키는 자다:

| 약속 | 오늘 `contain` 이 지키는 방법 |
|---|---|
| 쓸 수 있는 `$CUBRID`, 이 케이스 전에 복원됨 | 오버레이 상위 층 |
| `$CUBRID_DATABASES` 가 비어 있음 | 레지스트리 격리 |
| 포트 1523 이 이 케이스만의 것 | network 네임스페이스 |
| 돌고 있는 CUBRID 프로세스가 없음 | PID 네임스페이스 |
| 브로커 공유 메모리가 충돌하지 않음 | IPC 네임스페이스 |
| `java javac diff wget find cat kill tar expect` | 호스트에 있다고 점검 |
| `$init_path` · `$CTP_HOME` · `PATH` | prologue 가 설정 |
| bash 호환 `/bin/sh` | bind |

`Channel` (C3) 이 **"어디서 실행하는가"** 인 것처럼, 이것은 **"무엇 안에서 실행하는가"** 다. 둘은
직교한다: 슬롯은 로컬에도 원격에도 설 수 있고, 어느 쪽이든 케이스는 같은 것을 전제한다.

**결정 필요 — 이음매의 넓이.** 두 안이 있다.

| | |
|---|---|
| **좁게** | `Acquire(ctx) (Slot, error)` 만. Slot 은 `Channel` 과 자기 정리 책임을 갖는다. 케이스를 돌리는 쪽은 슬롯이 어떻게 만들어졌는지 모른다 |
| **넓게** | 위 표의 여덟 약속을 각각 메서드로 |

**좁게를 권한다.** 넓은 이음매는 `contain` 의 구현 세부를 인터페이스로 승격시키는 일이고,
두 번째 구현이 그 모양을 따를 이유가 없다. 컨테이너에는 "오버레이를 얹는다"가 없다 — 이미지가
그 일을 이미 했다.

### 2-3. 두 번째 구현 — csb 노드

노드가 슬롯이 되려면 셋이 필요하고, 둘은 길이 있다:

| | |
|---|---|
| shell 도구 (`java javac expect` …) | **세 번째 이미지 레시피.** `tailnetDockerfile` 이 선례이며, 그 주석이 왜 플래그가 아니라 별도 레시피인지 적어뒀다 — 이미지 태그가 레시피의 해시라 두 레시피는 두 이미지이고, HA 페어를 돌리는 사람이 JVM 을 받을 이유가 없다 |
| CTP 트리 | **마운트.** `--tools` 가 이미 호스트 디렉터리를 `/tools:ro` 로 넣는다. 이미지에 넣을 물건이 아니다 — 사용자의 체크아웃이고 버전이 다르며, 엔진과 같은 이유로 읽기전용이어야 한다. ADR-022 가 csb 에 남긴 요청 네 가지 중 하나가 정확히 이것이다 |
| 판정 파일이 나오는 길 | 노드의 `/results` 가 이미 호스트로 마운트된다 |

**레시피의 규율을 물려받는다.** `baseDockerfile` 의 주석이 *"Every line is load-bearing"* 이고 각
줄마다 **없으면 무엇이 어떻게 깨지는지**를 적는다. shell 레시피도 같은 기준을 만족해야 하고,
`expect` 는 이미 그 형태의 근거를 갖고 있다 — 없으면 216 케이스가 **돌긴 돌고** `.exp` 가 안
돌고 grep 이 0 을 세어 **틀린 답과 구별되지 않는 평범한 NOK** 가 된다.

### 2-4. 값이 무엇인가 — 그리고 무엇이 아닌가

**병렬성이 아니다.** 같은 머신에서 컨테이너 슬롯이 네임스페이스 슬롯보다 많이 설 이유가 없다.
둘 다 같은 코어와 같은 디스크를 쓴다.

**격리다.** 지금 슬롯은 `/tmp` 를 분리하지 않는다. 실제로 그것 때문에 `cub_master` 의 소켓
`/tmp/CUBRID1523` 에서 마스터 넷이 충돌했고, `CUBRID_TMP` 로 우회했다. **`/tmp` 아래에 고정
이름으로 쓰는 케이스는 여전히 다른 슬롯 및 머신과 그것을 공유한다.** 컨테이너에는 그 구멍이
없다. 이것이 오늘 이름 댈 수 있는, 측정 가능한 유일한 이득이다.

**그리고 잃는 것도 적어둔다.** shell 스위트가 지금 내세우는 성질이 *"root 도 컨테이너 런타임도
필요 없다"* 인데, 절반이 깨진다. rootless podman 이면 **root 는 여전히 불필요** 하고 런타임만
필요해진다 — csb 는 docker 와 podman 을 모두 몰고, 클러스터가 자기를 만든 백엔드를 기록한다.

## 3. 선택적 volatile — csb 안

### 3-1. 지금

`CSB_HOME` 이 상태 루트 전체를 정하고(`store.Open`), 노드의 `/work` 과 `/db` 는 그 아래를 bind
마운트한다. **그래서 `CSB_HOME` 을 tmpfs 위에 두면 오늘도 전부 RAM 에 올라간다.** 코드 변경이
필요 없다.

없는 것은 **선택** 이다. 전부 아니면 전무이고, 한 클러스터만 또는 한 노드의 `/db` 만 휘발로 두는
방법이 없다. `--shm-size` 는 공유 메모리지 저장소가 아니다.

### 3-2. 무엇을 선택 단위로 할 것인가

**결정 필요.** 세 후보:

| 단위 | 뜻 | 문제 |
|---|---|---|
| 클러스터 | `create --volatile` | 페어 하나가 통째로 RAM. 굵다 |
| 노드 | 노드마다 | 마스터는 디스크, 슬레이브는 RAM 같은 조합이 가능해진다 |
| 경로 | `/db` 만 휘발, `/work` 은 디스크 | 가장 가늘고 가장 설명하기 어렵다 |

**노드 단위를 권한다.** 배치가 노드 단위이므로(§4) 같은 축에 놓이고, "이 노드는 저 머신의
RAM 에" 가 한 문장으로 표현된다.

### 3-3. 반드시 함께 가야 하는 경고

**볼륨이 커지는 것을 먼저 막지 않으면 volatile 은 문제를 RAM 으로 옮길 뿐이다.** 측정된 사실이
그것을 말한다: 페어 하나가 2.9 GB 로 시작해 `_01_object` 한 바퀴에 7.5 GB 까지 간다. 데이터베이스가
스스로 볼륨을 늘리고 리셋은 그것을 돌려주지 않는다
([`evidence/ha/a-sandbox-pair-wears-out.md`](../evidence/ha/a-sandbox-pair-wears-out.md)).
이 머신은 31 GB 다. 8 페어 × 성장 = swap 이고, 그러면 오늘 관측된 **iowait 51.7%** 가 개선되는
것이 아니라 자리를 옮긴다.

그래서 volatile 에는 **상한과 그것을 넘었을 때의 행동**이 함께 있어야 한다. shell 스위트가
`scenario_ram_mb` 와 `scenario_ram_high_water` 로 이미 하는 것 — 레인을 나누고 압박을 감시하고
새 일을 거부하는 것 — 이 여기서도 필요하고, 그쪽에 이미 있는 판단을 다시 만들 이유는 없다.

## 4. 배치 — csb 안

[`evidence/ha/pairs-across-machines.md`](../evidence/ha/pairs-across-machines.md) 가 이미 설계다.
요약만 옮긴다:

- **프레임:** 로컬이든 원격이든 **csb 라는 하나의 도구를 쓴다.** 그 위의 두 번째 도구도, 호출자가
  고르는 모드도 없다. 표면은 자라지 않고 배치는 `create` 에 한 번 나타난다.
- **이미 있는 것:** `Node.Host` 가 아티팩트에 기록된다(오늘 들어감). `--network tailnet` 이
  머신을 걸치는 네트워크를 준다. fault 의 의미는 tailnet 에서도 그대로다.
- **없는 것:** 노드를 다른 머신에 **띄우는** 것. 그리고 notebook 에는 컨테이너 엔진이 없다 —
  그건 다른 도구가 아니라 **백엔드가 하나 더**(ADR-022 C5 의 netns) 필요하다는 뜻이다.
- **불변식:** 절단 동사가 자기 제어 채널을 자를 수 없어야 한다. 제어는 대역외, 절단은 테일넷
  주소에만.

## 5. 위의 층 — 축 O

### 5-1. 무엇을 소유하나

| | |
|---|---|
| 인벤토리 | 어떤 머신들이 있고 무엇을 할 수 있는가 |
| 배치 | 어느 샤드가 어느 머신으로 |
| 환경 | 각 머신에 무엇이 서 있어야 하는가 (csb 를 몰아서) |
| 수집 | 결과 트리를 모아 하나의 판정으로 |
| 보고 | 알림, 이슈 등록 — `migration-exclusions.md` 가 축 O 로 판정한 것들 |

### 5-2. 무엇을 소유하지 않나

**러너의 안쪽 전부.** 층은 `testkit shell -c <conf>` 를 부를 뿐이다. 그 명령은 동결돼 있고
(ADR-003), 그것이 층과 러너 사이의 계약이다. 층이 늘어도 러너의 표면은 한 글자도 안 바뀐다.

### 5-3. 무엇을 보내고 무엇을 보내지 않나

여기가 가장 틀리기 쉬운 자리다. 워커 하나가 shell 케이스를 돌리려면 셋이 필요하다:

| | 크기 | 출처 |
|---|---|---|
| 코퍼스 | 체크아웃 | git |
| CTP 트리 | 체크아웃 | git |
| 엔진 빌드 | ~934 MB | 빌드 산출물 |

**앞의 둘을 밀지 않는다.** 둘 다 git 저장소이고 동결돼 있다. 마스터가 그것을 보내면 git 이
이미 하는 일을 더 나쁘게 다시 구현하는 것이고, 더 나쁜 이유는 **워커가 자기가 무엇을 돌렸는지
말할 수 없게 되기 때문**이다. 스스로 clone 한 워커는 커밋 id 를 댄다.

**셋째는 csb 가 이미 답을 적어둔 질문이다.** [`02-topology.md`](../../../extensions/cluster-sandbox/docs/design/02-topology.md)
§4: *"`engine.identity` rather than `engine.path`. **A build tree does not travel**, so recording
its path alone reproduces nothing."* csb 는 엔진을 이미지에 넣지 않고 읽기전용으로 마운트하며
아티팩트에는 **정체** 만 기록하고, 빌드가 다르면 말해준다.

**그래서 층이 보내는 것은 다른 출처가 없는 것뿐이다** — conf, 샤드 목록, 패치 세트
(`overrides/patches/` 는 비공개 저장소라 워커가 스스로 못 가져올 수 있다). 전부 킬로바이트다.
그리고 **정체 셋**(코퍼스 리비전, CTP 리비전, 엔진 build id)을 함께 보내 워커가 대조하고 다르면
거부한다. csb 가 페어에 대해 하는 것과 같은 모양이다.

전송 수단은 이미 있다 — `exec.SSH` 의 `Put`/`Get` (C3).

### 5-4. 샤드는 이미 만들어져 있다

[`evidence/compare/shards.sh`](../evidence/compare/README.md) 가 코퍼스를 샤드로 자르고
`shard.sh` 가 샤드마다 `scenario=` 를 바꿔 한 번씩 돌린다. 동등성 비교가 이미 그렇게 전체
코퍼스를 돈다. **층은 그 루프를 여러 머신으로 펴는 것이고, 자를 방법을 새로 만들 필요가 없다.**

### 5-5. 그래서 오늘도 가능한 형태가 하나 있다

머신 A 에서 샤드 1–5, 머신 B 에서 6–10 을 각각 `testkit shell` 로 돌리고 합치는 것. 러너 안에
fleet 을 넣지 않고 러너 **위에서** 분배한다. 필요한 것은 각 머신에 체크아웃과 엔진이 있는 것,
그리고 머신마다 자기 `CTP_HOME` 을 쓰는 것뿐이다(동시에 두 런이 거부되는 이유가 결과 트리
공유이므로). **층의 첫 버전은 이 셸 루프여도 된다.**

## 6. 순서, 그리고 그 앞에 있는 것

### 6-1. 재는 것이 먼저다

ADR-014 가 fleet 을 닫은 근거는 **CTP 가 그렇게 쓰이지 않았다**는 측정이었다. 그것을 뒤집을 수
있는 증거는 **한 머신이 정말로 부족하다**는 측정이다.

오늘 그 계기로 보이는 숫자가 하나 나왔다 — 16 코어에 로드 8.3, **CPU 의 절반이 iowait**. 그러나
**그 읽기는 근거가 되지 못한다.** 같은 머신이 페어 하나만 돌 때 iowait 4% 다. 51.7% 는 머신의
성질이 아니라 그때 올려둔 부하(페어 11 개, 그중 하나는 127,114 페이지까지 닳은 것)의 성질이었다.
한 번의 읽기로 정할 수 있는 것이 아니다.

**그러므로 필요한 것은 실제 워크로드 아래의 측정이다** — 전체 코퍼스 한 바퀴를, 슬롯 수를 바꿔
가며, 머신 패널을 보면서. 답이 둘로 갈린다:

| 무엇이 지배하는가 | 처방 |
|---|---|
| iowait | **이 머신의 디스크.** NVMe 하나가 층 전체보다 싸다 |
| CPU, 그리고 슬롯이 무릎에 걸림 | **머신이 더 필요하다.** 그때 축 O 가 근거를 갖는다 |

둘은 완전히 다른 처방이고, 지금 가진 증거로는 어느 쪽인지 말할 수 없다.

**그래서 shell 전체 코퍼스를 한 번 돌리며 머신 패널을 보는 것이 이 문서의 어느 항목보다
앞선다.** 도구는 오늘 붙었다.

### 6-2. 그다음 순서

1. **슬롯 제공자 이음매** (§2-2). 나머지가 그것 없이는 쓸 데가 없고, 이음매가 생기면 "csb 노드를
   슬롯으로"는 두 번째 구현일 뿐이 된다.
2. **세 번째 이미지 레시피 + CTP 트리 마운트** (§2-3). 이음매의 첫 소비자.
3. **노드 단위 volatile** (§3), 상한과 함께.
4. **배치** (§4), 그리고 netns 백엔드.
5. **층** (§5). 첫 버전은 셸 루프.

### 6-3. 그리고 이 문서가 열지 않는 것

**게이트가 먼저다.** 3 단계의 ADR-013(shell 전체 코퍼스 비교)과 4 단계의 ADR-019(isolation
컨트롤러, 27 케이스가 통과 못 함)가 열려 있다. 게이트가 안 닫힌 러너를 여러 머신에 뿌리면
동등성 비교 자체가 어려워진다 — 지금은 두 러너의 파일을 한 머신에서 비교하는데, 분배가 끼면
어느 차이가 러너의 것이고 어느 것이 머신의 것인지 한 겹이 더 생긴다.

## 7. 러너가 이미 들고 있는 축 O

층이 없으니 러너가 축 O 를 조금씩 흡수해 왔다. 흡수는 대부분 필요해서 일어났다 — 층이 없는
동안 누군가는 해야 했다 — 그러나 **기록하지 않으면 굳는다.** 이 절이 그 기록이다.

판정은 이 프로젝트 자신의 질문으로 한다:
[`migration-exclusions.md`](../concept/migration-exclusions.md) §0, ***이 기능이 없어도 테스트는
정확히 같은 결과를 내는가?*** 예면 축 O 다.

| 지금 러너에 있는 것 | 판정 | 왜 여기 있게 됐나 | 층이 생기면 |
|---|---|---|---|
| **`sandbox_pairs` 로 페어를 세우고 치우기** (`harepl.go`, 2026-09-23) | **축 O.** 페어를 손으로 받았든 런이 만들었든 판정은 같다. 제외 목록의 `DeployOneNode.deploy_build_on_linux` 와 `TestFactory.concurrentDeploy`(N대 동시 배포)가 정확히 이 모양이다 | 여덟 페어를 손으로 세우고 conf 를 여덟 번 고치는 것이 실제로 측정을 막았다 | **층으로 옮긴다.** 러너는 `sandbox_cluster` 로 받은 것을 쓰기만 한다 |
| **`reportStanding`** — 서 있는 세트와 용량 보고 | **축 O.** 순수한 운영 보고 | 56 GB 가 될 때까지 아무도 몰랐다 | **층으로.** 또는 `csb cluster ls` 에 이미 있으니 지워도 된다 |
| **상태 페이지의 machines 절과 클러스터 표** | **경계.** 슬롯·케이스·판정은 축 T(런에 관한 것), 머신과 클러스터 목록은 축 O(환경에 관한 것) | 같은 페이지에 있는 것이 자연스러웠다 | **절을 갈라 옮긴다.** 런 진행은 러너가, 환경은 층이 |
| **`testkit watch`** | **축 O.** `migration-exclusions.md` §152 가 *"결과 조회 UI — 축 O"* 라고 이미 판정했다 | 돌고 있는 런을 볼 방법이 없었다 | **층으로.** 여러 머신의 런을 한 페이지로 보는 것이 층의 일이다 |
| **`TESTKIT_HA_REBUILD`** — 크기가 안 맞는 세트 재건 | **축 O.** 환경 수명주기 | 위 첫 줄의 따름정리 | 첫 줄과 함께 간다 |
| `testkit sizing` / 슬롯 수 자동 결정 | **축 T 로 남는다.** [ADR-020](../adr/ADR-020-sizing.md) 이 이것을 **런 자신의 결정**으로 정했고, 근거는 슬롯 수가 판정을 바꾸지 않도록 *측정으로* 정해진다는 것이다. 한 머신 안의 결정이라 인벤토리가 아니다 | — | 그대로 |
| `internal/sandbox` 의 fault 동사 | **축 T.** 고장은 **시험 대상**이지 운영이 아니다. group B 가 묻는 질문 자체다 | — | 그대로 |

### 7-1. 그래서 지금 무엇을 하나 — 아무것도 되돌리지 않는다

되돌리면 측정이 멈춘다. `sandbox_pairs` 가 없으면 여덟 페어 측정을 손으로 세우는 일로 되돌아가고,
그건 오늘 이 문서가 인용하는 숫자들이 나오지 못했을 조건이다.

**대신 셋을 한다.**

1. **표시한다.** 위 표가 그것이고, 이 문서가 그 표의 집이다. 축 O 로 판정된 코드에는 그렇다는
   주석을 단다 — *"이것은 축 O 이고, 층이 생기면 옮긴다"* — 그래야 다음 사람이 이것을 러너의
   본질로 읽지 않는다.
2. **넓히지 않는다.** 러너에 축 O 를 **더** 넣지 않는다. 새 환경 기능이 필요하면 그것은 층의
   첫 요구사항이지 러너의 다음 플래그가 아니다. 구체적으로: 알림, 이슈 등록, 인벤토리, 머신 간
   분배는 러너에 들어오지 않는다.
3. **표면을 좁게 유지한다.** 축 O 로 판정된 것은 전부 **conf 키이거나 환경변수**이고 명령줄이
   아니다. 명령줄은 동결돼 있고(ADR-003) 층과 러너 사이의 계약이므로, 층으로 옮길 때 명령줄이
   바뀌지 않아야 옮기는 일이 하루로 끝난다. 오늘 `TESTKIT_HA_REBUILD` 를 플래그가 아니라
   환경변수로 둔 판단이 마침 이 규칙과 같은 방향이었다.

### 7-2. 이것이 ADR-014 위반인가

**아니다, 그러나 아슬아슬하다.** ADR-014 가 금지한 것은 *함대* — 인벤토리, 여러 머신에 배포,
기계 간 분배, 실행 중 기계 추가/제거 — 이고 러너는 그 넷 중 어느 것도 하지 않는다. 페어를 세우는
것은 **한 머신 위에서** 일어나고, 러너는 여전히 자기가 어디 있는지만 안다.

그러나 "환경을 세운다"는 fleet 의 첫 성분이다. 다섯 번째 성분이 들어오는 순간 — 예컨대 "이 페어는
저 머신에" 가 conf 키가 되는 순간 — ADR-014 는 실제로 깨진다. **그 줄이 이 문서의 §1 이 그은
줄이고, 그것을 넘는 기능은 층에 속한다.**

## 8. `testkit-cluster` 라는 저장소를 만들어 둘을 물게 하는 것이 맞나

**판정: 지금은 아니다. 그리고 만들 때가 와도 "둘을 담는 껍데기"로 만들면 안 된다 — §5 의 층이
코드를 갖고 태어나면서 둘을 소비하는 형태여야 한다.**

### 8-1. 제안이 옳게 짚은 것

지금의 배치는 **방향을 주장한다.** `cubrid-testkit` 이 `extensions/cluster-sandbox` 를 물고 있고,
이것은 "testkit 이 csb 를 쓴다"로 읽힌다. 그런데 csb 자신은 관계를 **대등하게** 적어뒀다:

> **`cubrid-testkit`** consumes this tool: it owns suites, dispatch and reporting;
> **this project owns the environment they run on.**

그리고 §1 이 방금 그은 줄에서 그 주장은 **틀리게 된다.** 층이 생기면 둘을 모는 것은 층이고,
층이 testkit 안에 있으면 testkit 이 오케스트레이터가 된다 — §1 이 하지 말라고 한 바로 그것이다.
제안은 이 긴장을 정확히 짚었다.

### 8-2. 그런데 지금 옮기면 깨지는 것 — 서브모듈은 의존이 아니라 **핀**이다

[ADR-022](../adr/ADR-022-topology-provider.md) 의 대안 절이 "vendor 하지 말고 `csb` 를 PATH 에서
찾자"를 검토하고 기각했다. 기각 사유가 이 판정을 지배한다:

> Rejected because **the pin is the point** — evidence produced here names which revision of the
> provisioner produced the topology, and **a tool found on PATH names nothing.**

testkit 은 csb 에 **컴파일되지 않는다.** 서브프로세스로 몰고 JSON 을 읽을 뿐이다
(ADR-001 Consequence 4). 그러니 서브모듈은 빌드 의존이 아니라 **증거의 일부** 다 —
`evidence/ha/` 의 모든 발견이 "어느 리비전의 provisioner 가 이 토폴로지를 만들었는가"를 댈 수
있는 이유가 그 핀이다.

**증거는 testkit 안에 산다.** `docs/project/evidence/ha/` 가 거기 있다. 핀을 부모 저장소로
올리면, **testkit 만 clone 한 사람은 자기 증거가 무엇 위에서 나왔는지 말할 수 없다.** 그것이
ADR-022 가 PATH 방식을 기각한 바로 그 상태다. 형태만 다르고 결과가 같다.

### 8-3. 그리고 쓰지 않는 사람에게 비용을 물린다

`shell` 이나 `sql` 을 돌리는 사람은 csb 를 만질 일이 없다. 지금 배치에서 그것은 `extensions/`
아래의 선택 사항이다 — README 가 *"separate repositories testkit will drive"* 라고 부르는 자리.
부모 저장소로 묶으면 그 사람이 쓰지도 않을 것을 위해 superproject 를 clone 한다.

### 8-4. 그래서 어떤 형태가 맞나

| 안 | 판정 |
|---|---|
| **지금 그대로** — testkit 이 csb 를 핀으로 문다 | **맞다, 층이 없는 동안은.** 핀이 증거와 같은 저장소에 있다 |
| `testkit-cluster` 가 **둘을 담는 껍데기** (자기 코드 없음) | **아니다.** 핀을 증거에서 떼어놓고, 저장소를 하나 더 만들어 태그·릴리스를 하나 더 늘리며, 그 대가로 사는 것이 "대등해 보임" 뿐이다 |
| `testkit-cluster` 가 **§5 의 층** (인벤토리·배치·수집을 자기 코드로 갖고, 둘을 소비) | **맞다, 그때가 오면.** 그리고 그때 **testkit 은 csb 핀을 그대로 유지한다** — 층이 없이 testkit 만 쓰는 사용법이 사라지지 않기 때문이다 |

셋째 안에서 층은 둘을 **testkit 이 csb 를 소비하는 방식 그대로** 소비한다: 서브프로세스와
아티팩트, 링크하지 않음. 그러면 핀이 두 곳에 생기는데 그것은 중복이 아니라 **각자의 증거가 각자
무엇 위에서 나왔는지 말하는 것**이다. 층의 증거는 층의 핀이 설명한다.

### 8-5. 지금 대신 하는 것 — 방향 주장을 문서로 중화한다

저장소를 옮기지 않고 같은 오해를 막는 값싼 방법이 있다. `extensions/` 의 README 가 이미 절반을
했다 — `cluster-sandbox` 는 **E 번호가 아니다**, 테스트 능력이 아니라 **환경 제공자**다, 라고
적어뒀다. 여기에 한 줄이 빠져 있다: **이 위치는 소유가 아니라 핀이고, 층이 생기면 층도 같은
것을 물되 이 핀은 남는다.**

그 한 줄이 §8-4 의 셋째 안을 예고해두므로, 나중에 층을 만들 때 "그럼 testkit 의 서브모듈을
없애야 하나"라는 질문이 다시 나오지 않는다.

### 8-6. 다시 판정해야 할 조건

이 판정은 **증거가 testkit 에 있다**는 사실에 걸려 있다. 만약 HA 증거가 층으로 옮겨가거나
(여러 머신의 측정은 층이 만들 테니 그럴 수 있다), csb 가 컴파일 의존이 되면 — 둘 다 오늘은
아니다 — 이 절을 다시 연다.
